## Diagnosis: Severe network/interconnect degradation (ongoing)

**Evidence:**
- **Telemetry pipeline:** `otel-collector` and `prometheus` are UP; NCCL counters are actively advancing (not frozen). Only `vllm-golf`/`vllm-bravo` are DOWN, which is normal idle-workload noise, not a fault.
- **Onset:** At **11:37:57**, all four ranks *simultaneously* dropped from a steady ~78.8 MB/s to **0 B/s** — same timestamp across bravo (ranks 0,1) and golf (ranks 2,3), i.e. no stagger. Since then, throughput has stayed collapsed, with only occasional tiny trickles (1.1–2.8 MB/s for a single 15s sample) rather than any sustained recovery. This pattern persists through the most recent samples — **the fault is still active now**, not resolved.
- **Per-rank comparison:** Over a 5-minute window all ranks track each other at ratio ~1.00 — perfectly uniform, no single rank/host diverging.
- **GPU clocks (`DCGM_FI_DEV_SM_CLOCK`):** All four ranks read 2790–2820 MHz, ratio ~0.99–1.01 — normal and uniform. Ruled out a clock clamp.

**Ruled out:**
- Collector kill — collector is UP and counters are still (barely) moving.
- GPU clock clamp — clocks are uniform and healthy across all ranks.
- A single dead rank — no stagger; all four stopped at the exact same instant, and none are fully frozen (small trickles continue), which is inconsistent with one rank dying and the rest blocking.

**Conclusion:** This is interconnect degradation, and a severe one — throughput didn't just dip (as in a typical netem delay case, ~1/3 of baseline), it collapsed to near-zero for both nodes simultaneously and is only trickling small amounts through since 11:37:57. All ranks are affected uniformly (consistent with all-reduce synchronizing on the shared collective), and the fault is ongoing at present. Per the tooling's known limitation, node-level network counters can't localize this to a specific physical link — I can confirm the fault type (interconnect degradation, ongoing since 11:37:57) but not which physical cable/switch is at fault.
